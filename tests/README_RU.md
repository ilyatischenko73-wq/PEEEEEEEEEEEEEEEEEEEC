Тесты PEEC после изменений
=========================

Набор входит в исправленный PEEC.zip и использует COMMON_SOURCES из Makefile.
Исторические результаты исходного архива оставлены в BASELINE_RU.md.
Актуальные протоколы находятся в reports/, описание изменений — в ../README_RU.md.

1. Распакуй полный PEEC.zip в новую папку и открой терминал в каталоге PEEC.

2. Из корня PEEC выполни основной набор:

   ```bash
   make -f Makefile.tests verify
   ```

   Нужны GNU Make, GCC с OpenMP и Python 3.10 или новее. Команды проверены под
   Linux. Нативная Windows-сборка здесь не проверялась. Явные CLI-аргументы
   теперь принимаются на всех ОС, файловый режим выбирается через --config FILE.

   Команда `make test` из основного Makefile запускает этот же набор.
   Отдельные тестовые программы используют объекты в build/verification.

3. Отдельно проверь время жизни строк конфигурации под ASan/UBSan:

   ```bash
   make -f Makefile.tests verify-asan
   ```

   Эта цель требует поддержки AddressSanitizer/UndefinedBehaviorSanitizer в GCC.
   Она вызывает настоящий файловый парсер из src/main.c и читает строки после
   возврата из него. Если парсер освобождает их раньше времени, проверка падает.
   LeakSanitizer в этом узком probe отключён: полный жизненный цикл приложения
   здесь не выполняется, а проверка утечек не входит в контракт этого теста.

4. Если менялся SPICE-экспорт, запусти его проверки:

   ```bash
   make -f Makefile.tests verify-spice
   ```

   Дополнительно нужны NumPy и SciPy в том Python, который запускает Make.
   При необходимости задай интерпретатор явно:

   ```bash
   make -f Makefile.tests verify-spice PYTHON=/path/to/python3
   ```

   Этот тест заново собирает матрицы пластины, создаёт netlist с нулевым
   отсечением и восстанавливает C из реально записанных конденсаторов.
   Проверяется точность относительно P^-1 и порядок run/tran перед wrdata.
   Явный отказ экспортировать непредставимую точно модель с понятной
   диагностикой также допустим. Проверка не запускает ngspice.

   Если ты заменишь RLC-представление управляемыми источниками, сравнение только
   конденсаторов нужно заменить сравнением полного нового оператора или
   результатов симуляции. Такой экспорт текущий тест не сертифицирует.

Основной набор содержит 23 проверки (17 исходных и 6 дополнительных):

| Тест | Что проверяется | Критерий |
| --- | --- | --- |
| quadrature_geometry | Поворот, перенос и изменение масштаба панели | Кубический закон масштабирования; ошибка < 0,1% |
| quadrature_partition | Сумма интегралов по двум соседним панелям | Совпадение с целым прямоугольником < 0,1%; взаимность |
| quadrature_near_far | Близкие параллельные панели и удалённая пара | Предел self и геометрические границы 1/R |
| harmonic_loop_reference | Токовая петля и градиентное возбуждение в SI на трёх частотах | Аналитические токи и потенциалы, ошибка < 1e-6 |
| complex_lu_singular | Действительно вырожденная матрица | Ненулевой код ошибки |
| config_file_cli | Полный запуск --config через главный драйвер | Успешное чтение и завершение mesh-info |
| real_lu | Вещественная система с известным решением и необходимой перестановкой строк | Ошибка решения < 1e-11 |
| complex_lu | Комплексная система с известным решением | Ошибка решения < 1e-11 |
| backward_euler_order | LC-задача с взаимной электростатической связью | При делении dt на 2 отношение ошибок около 2; энергия не растёт |
| trapezoidal_order_energy | Та же аналитическая LC-задача | Отношение ошибок около 4; дрейф энергии < 1e-11 |
| shunt_energy_ohm | Резистивный шунт на двухузловой модели | Закон Ома, сохранение заряда, дискретный баланс энергии с потерями |
| quadrature_square | Аналитический self-интеграл квадрата | Относительная ошибка <= 0,1% |
| quadrature_rectangle10 | Прямоугольник 10:1 | Относительная ошибка <= 0,1% |
| quadrature_rectangle100 | Прямоугольник 100:1 | Относительная ошибка <= 0,1% |
| aperture_valid | Правильная карта и знак переноса тока | Успех и ожидаемый ток |
| aperture_reject_geometry | Узлы ошибочно сопоставлены через 100 м | Функция должна вернуть ненулевой код |
| harmonic_1MHz | Полный расчёт plate.msh | Успех и конечная обратная ошибка <= 1e-9 |
| harmonic_1Hz | Та же геометрия на 1 Гц | Успех и конечная обратная ошибка <= 1e-9 |
| harmonic_1kHz | Та же геометрия на 1 кГц | Успех и конечная обратная ошибка <= 1e-9 |
| rcs_valid_order | ЭПР пластины с поддерживаемой квадратурой | Две строки CSV, конечная положительная ЭПР для выбранных направлений |
| rcs_reject_order7 | Неподдерживаемый порядок квадратуры | Диагностика и ненулевой код завершения |
| case_scattering | Аргументы run_scattering.cfg | Парсер принимает и валидирует конфигурацию |
| case_rcs | Аргументы run_rcs.cfg | Парсер принимает и валидирует конфигурацию |

Порог 0,1% — заданная цель точности локальной квадратуры для этих тестовых
геометрий. Он не задаёт автоматически такую же погрешность итогового тока или ЭПР.
Порог находится в QUADRATURE_REL_TOL в tests/test_core.c. Изменять его следует
по принятому бюджету точности задачи, а не ради получения PASS.

Тесты временных схем используют L=1, R=0, A=[-1,1] и
P=[[1,0.25],[0.25,1]], поэтому взаимная электростатическая связь ненулевая.
Для I(0)=1, Vc(0)=0 точное решение имеет частоту omega=sqrt(1.5):
I(t)=cos(omega*t), Vc(t)=[-sin(omega*t)/omega,+sin(omega*t)/omega].
Сравниваются решения на t=1 при dt=0.1, 0.05, 0.025. Допустимое отклонение
отношения ошибок от 2 или 4 составляет 10%.

Для шунта проверяется баланс схемы трапеций:
E[n+1]-E[n]+dt*R*((Ish[n]+Ish[n+1])/2)^2=0.
Также проверяются закон Ома и сохранение суммарного заряда.

Успешный основной прогон заканчивается строкой:

```text
RESULT: 17 PASS, 0 FAIL
```

Любой FAIL даёт ненулевой код завершения Python и Make. Известные ошибки
исходника не помечены как допустимые падения: после их исправления они должны
стать PASS. Если выбрана неизвестная проверка или не запущено ни одной,
runner также завершается с ошибкой.

Полный stdout/stderr каждого подпроцесса, команда запуска, CSV и report.json
пишутся в новый каталог build/verification/runs/run-... . Путь к отчёту
печатается в конце. Каждый прогон получает свой каталог, чтобы не использовать
старые результаты вместо новых. В JSON записаны имя теста, статус, детали,
длительность и относительный путь к логу.

Для работы над одной частью доступны команды:

```bash
make -f Makefile.tests verify-core
make -f Makefile.tests verify-cli
```

После первой сборки можно повторить ровно один тест:

```bash
python3 tests/run_tests.py --group core --only trapezoidal_order_energy
python3 tests/run_tests.py --group cli --only harmonic_1kHz
```

После изменения C-кода сначала запускай соответствующую цель Make: прямой
вызов Python не компилирует исходники. Зависимости от заголовков отслеживаются
через .d-файлы. Если меняешь именно флаги компиляции, принудительно пересобери:

```bash
make -B -f Makefile.tests verify
```

После зелёного набора переходи к проверке конкретной физической задачи:

1. Зафиксируй геометрию, материал, источник, физические координаты контактов и
   наблюдаемую величину, например ток шунта I_shunt(t). При перестроении сетки
   сохраняй физическое положение контактов; номера узлов могут измениться.
2. На одной сетке сравни dt, dt/2, dt/4 в одинаковые моменты времени. Проверяй
   форму кривой, максимум и время максимума, а также заряд и энергетический баланс.
   На реальном импульсе с особенностями порядок оценивай в режиме сходимости.
3. При достаточно малом dt сравни три последовательно уточнённые сетки.
   Перестань уменьшать dt только после того, как его ошибка станет меньше
   наблюдаемой сеточной ошибки. Допуск на физический результат задай заранее.
4. Для RCS выбери эталон с известным решением или независимый EM-решатель
   и одинаковые соглашения об углах/поляризации. При квазистатическом ядре
   сначала проверяй электрически малые объекты.
5. Для SPICE сравни токи/напряжения на одинаковых входных данных и по шагу
   времени; одной успешной генерации netlist недостаточно для такого сравнения.

Набор не проверяет полноценную модель запаздывания, всю геометрию slot-cells,
все режимы GUI и длительный расчёт корпуса. Тесты примеров .cfg проверяют
парсинг и валидацию параметров, без дорогостоящей сборки этих моделей.

Если после изменений изменится API (в частности, файловый парсер из main.c),
нужно адаптировать вызовы тестов к новому интерфейсу, сохранив физические
эталоны и критерии. Результаты исходной версии находятся в BASELINE_RU.md.
